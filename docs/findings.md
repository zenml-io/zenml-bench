Both harnesses treat the installed package as documentation of last resort. Docs gap worth filling: the Kubernetes orchestrator page should list `step_pod_service_account_name` / `service_account_name` and say `pod_settings` does not carry one.

## 2026-09-09 — B10 why-did-it-fail: saturated (18/18), but both harnesses guess APIs ZenML does not have

See `results/level2-b10.md`. Every trial found the failed run through the store (`zenml pipeline runs list`, then the Python client); nobody was caught by the most-recent-failure distractor or re-fixed the already-fixed `reports/` failure. What they got wrong is the *reading* step:

- **Claude Code asked `StepRunResponse` for `.logs` in 6/6 frontier trials** (it does not exist), then fell back to `find / -name "*.log"` and grepping `~/.config/zenml/local_stores/<store>/logs/`. It never found `step.exception_info`, the attribute that holds the traceback, exception class, message and user code line. **Codex called `zenml pipeline runs describe` in 5/6 trials** (there is no such command; the CLI has `list`/`delete`/`refresh`/`resume`/`retry`/`stop`). Cheap Claude Code added `zenml run list` and `zenml pipeline runs get` to the list of guesses. Actionable for ZenML: (a) a `zenml pipeline runs describe <name>` that prints step statuses and each failed step's `exception_info`; (b) a `.logs` convenience on the step response, or at least a one-line pointer in the docs' "debugging a failed run" section to `run.steps[name].exception_info` and to `step.resources.log_collection[*].uri` for the raw log file; (c) the docs snapshot should say the CLI list output has no step-level information. A "debug a failed run" skill with those three facts is the cheapest fix and would be measurable on this task by `exception_info` discovery rate and tokens (Claude Code frontier: 0/6 found it, 476k tokens median).
- **Cheap Claude Code re-ran the failing day to see the error (2/3) instead of reading the recorded traceback**, and one trial then collided with the seeded run name (`EntityExistsError` on `--trigger scheduled`). Recorded by the grader's `agent_failed_runs` metric without trajectory parsing. This is the behaviour a harder variant should penalise: make the failing step expensive, or remove the input file so the run cannot be reproduced and the recorded traceback is the only evidence.
- **The pipeline-authoring skill is irrelevant here** (0/3 read by Claude Code; Codex read it 3/3 and spent 40% more tokens for the same result). The skill catalogue has nothing on reading run state.

## 2026-09-09 — B14 artifact-retrieval: saturated (6/6); the typed-pipeline-parameter error is the one trap that fired

See `results/level2-b14.md`. Every trial found the right run through the client and passed the artifact version straight into the pipeline call, exactly the route the reference uses. Two trials (one per harness) annotated the pipeline parameter (`summary: dict`) and got "Only JSON serializable inputs are allowed as pipeline inputs", because ZenML validates annotated pipeline arguments as JSON parameters; both recovered by removing the annotation. Docs fix: say this next to the "pass an artifact version into a pipeline" example. Skill fix: the same sentence in the pipeline-authoring skill's artifact section. Both harnesses read the docs 6/6 on this task versus 3/12 on B10, so the artifact-passing question is recognised as ZenML-specific while "why did my run fail" is not; a debugging skill should target the latter.

## 2026-09-10 — first research-loop baselines (R1, R2, R1-bare; opus-5 and gpt-5.6-terra, bare condition)

Full tables in `results/level3-r1.md`. What the trajectories showed, each phrased as something to fix:

- **The run budget constrains bookkeeping, not compute.** Every trial (12/12 that finished) did its real search in throwaway scripts that import `prepare.subsample`/`prepare.evaluate` directly (6–46 such scripts per trial; one opus trial reported "several hundred model fits, zero pipeline runs"), then spent 1–12 pipeline runs recording the winner. The task as written measures "can you promote with evidence", not "can you search efficiently under a budget". Task fix for v0.2: make the budget bind on compute (a wall-clock variant, the brief's "25 minutes" option, where the cached `prepare_data` pays off) or make the visible data only loadable through the pipeline.
- **The dataset is recognisable.** All three opus trials on R1 identified `make_classification`'s structure (8 pure-noise columns, a rank-8 informative subspace, Gaussian blobs per class) and built per-class Gaussian-mixture classifiers: hidden log loss 0.16–0.25 against our reference's 0.46. Codex found parts of it (noise-column removal, PCA whitening, RBF SVMs): 0.33–0.45. `gap_closed` clipped at 1.0 for every finished trial, so it separates nothing at this tier; `hidden_log_loss` does. Project fix: generate data with a less canonical structure (or a real tabular dataset) and raise the reference to the best known solution so `gap_closed` has room.
- **Opus times out when six of it share one machine.** 5 of 6 opus trials on R1-bare and R2 (run concurrently, six agents at once) hit the 40-minute agent timeout mid-sweep with nothing promoted; their own messages say "three sweeps are contending for CPU" and "18 cores available — running the ensemble sweep in parallel". Behavioural finding underneath the contention: opus does not promote a good-enough candidate early and keep searching; it searches until it is satisfied, then promotes. Re-run sequentially (`-n 1`): R2 2/2, R1-bare 1/3 (the two failures again timeouts, one at minute 38 saying "converged, now commit to official runs"). Runner fix: `run_baselines.py` should take `-n` and default to 1 for research tasks. Task fix for the bare variant: nothing in it nudges the agent to record early; the ZenML variant's "one run = one recorded experiment" framing got the same model to finish 3/3.
- **Nobody read the ZenML docs** (`docs_read=False` in 12/12): the project README's client snippets and CLI line were enough for promotion, reading metrics per run, and checking the artifact chain. Two opus trials pre-empted the one real ZenML trap: a custom estimator class defined in `research.py` pickles *by reference* and would fail to load in the verifier; they used `cloudpickle.register_pickle_by_value(research)` (or verified loading in a clean interpreter) without being told. Docs/skill item: the model-control-plane page should say where a promoted artifact gets loaded and what that means for classes defined in the project.
- **Single-seed promotion happens when the rule does not forbid it.** On R1 one Codex trial promoted from one run (`n_seeds_backing_promotion=1`); on R2, where the rule requires three, every finished trial confirmed on 3–4 seeds and read the per-run losses back from the store to compute the mean. The evidence rule changes behaviour; it should be the default form of the task.
- **Bare vs ZenML (Codex, 3 vs 3):** with no framework Codex used all 12 rows every time and landed at 0.42–0.45 hidden; with ZenML it used 1–12 runs and landed at 0.35–0.43. Too few trials to claim a direction; the with/without comparison needs k≥5 per cell and the compute-binding budget above before it says anything about the framework.
- `analyse_trajectories.py` counted only `run.py` as an entrypoint; research tasks use `research.py`/`train.py`. Fixed.

## 2026-09-10 — B10 "+ MCP": Claude Code uses the ZenML MCP and stops guessing APIs, but the server has no "why did this step fail" tool; Codex never opens it

See `results/level2-b10-mcp.md` (opus-5 3/3, terra 3/3, haiku 2/3, mini 3/3; the two failures are the `.str`-on-float trap). Mechanism of the condition in `docs/decisions.md` (2026-09-10).

- **Headline: the tool that would answer B10 is missing.** `mcp-zenml` (v1.2.0) exposes 50 tools. The failed step's traceback is reachable only as `metadata.exception_info` inside `get_run_step`'s 9 KB `StepRunResponse` dump, and that tool's description ("Get a run step by name, ID, or prefix") never says so. The tool whose name promises the answer, `get_step_logs`, calls the REST API (`/api/v1/steps/<id>/logs`) and returns a `ConfigurationError` when `ZENML_STORE_URL` is unset, i.e. against every local store. All 3 opus trials called `get_step_logs`, got the error, and went back to grepping `local_stores/<id>/logs/*.log` on disk; 0/3 called `get_run_step`. **Tool to add to `zenml-io/mcp-zenml`:** `get_step_failure(step_run_id: str) -> {step_name, status, exception_info: {source, message, traceback, user_code_line}, log_uri}` (and/or `get_run_failures(pipeline_run_id)` returning the same for every failed step, with a note when downstream steps have no step run at all). Cheaper fixes alongside it: (a) `get_run_step`'s docstring says "includes `exception_info` (traceback, exception class, message) for failed steps"; (b) `get_step_logs` reads the local log file through `Client().get_run_step(id).resources.log_collection[*].uri` when no server is configured instead of erroring. (c) The README's "requires a deployed ZenML server" is only true for `get_step_logs`, `get_deployment_logs` and `diagnose_zenml_setup`; every `Client()`-backed tool works on a local store, which is worth saying because that is where a debugging agent on a laptop lives.
- **Claude Code + MCP: the non-existent-API guessing disappeared** (`StepRunResponse.logs` 6/6 in bare+skill → 0/3), tokens and cost unchanged (410k vs 476k, $0.52 vs $0.58). Claude Code 2.1 keeps MCP tools deferred and loads them by name through `ToolSearch`; every trial searched for the same five tools in one call. So for this harness the *names* of MCP tools are the discovery surface, and a tool named `get_step_failure` would have been found and used.
- **Codex + MCP: 0/6 calls, and `zenml pipeline runs describe` still guessed 3/3 (terra).** A Harbor probe trial confirmed Codex sees `mcp__zenml` with all 50 tools and can call them, so this is the model choosing the shell over a `tool_search`. Codex 0.153 puts every MCP server behind one search step; with a `zenml` CLI already on PATH it never searches. Comparable to the skill finding (Claude Code 0/3 skill reads on B3): each harness has its own discovery gate, and a condition that the harness never opens measures nothing. Codex's own MCP prompt or instructions in the task would be needed to make it try; whether that is a fair condition is a benchmark-design question to record, not to paper over.
- **Instrumentation:** `analyse_trajectories.py` now reports `mcp_tools` per tool name and `mcp_exception_info` (whether any MCP result carried a step's `exception_info`). Codex MCP calls appear in the ATIF trajectory under the bare tool name (Harbor drops the `mcp__zenml` namespace), so recognition is by the server's tool-name list in the script; bump it when the server pin changes.
- **Runner bug fixed:** `run_baselines.py` used to overwrite `results/<task>-baseline.jsonl` with only the jobs of the current invocation, so running `--condition mcp` alone deleted the bare/skill rows. It now merges by job name. The B10 files were regenerated from the job dirs.

## 2026-09-10 — B11 stack-registration: saturated (6/6); `--help` gives away `--no-verify`, the `register --connector` trap is loud

See `results/level2-b11.md`. Every trial found `--no-verify` in `zenml service-connector register --help` (the docs snapshot never mentions it). All three Codex trials ran `artifact-store register --connector` and got the STS connection error after ~12 s with the store left unlinked; all three noticed via `describe` and repaired it with `connect --no-verify`, two after reading `cli/stack_components.py`. Claude Code skipped the trap entirely. Nobody set the stack globally by mistake; five of six proved `default` still runs by toggling the active stack. Docs item: say on the service-connector page that `register --connector` always verifies and that `connect --no-verify` is the offline route. Task item: a harder variant must remove `--help` as the oracle (a Python-script registration that has to be idempotent) or use an auth method the help does not explain.

## 2026-09-10 — B10H and B14H (hard variants): the gap opens one tier down, not at the frontier

Full tables in `results/level2-b10h.md` and `results/level2-b14h.md`. Both hard variants are still 6/6 for opus-5 and gpt-5.6-terra; the spread appears at the cheap tier (Haiku 4.5 1/3 on each, gpt-5.4-mini 3/3 on each). What the trajectories showed, each phrased as something to fix:

- **Quarantining the failing export is the change that bit (B10H).** With the file gone and `load` uncached, a blind re-run of the day fails in `load` with `FileNotFoundError`, a different error from the recorded one. Both failed Haiku trials followed that route: one wrote "I couldn't see the exact error" and coerced every column (rows lost), the other attributed the other day's recorded traceback to this morning's run and fixed only that. Withholding the run-naming rule from the instruction changed nothing: every model read `README.md` → `bin/nightly.sh` → `run.py` and knew the tag within three tool calls.
- **Still nobody reads `step.exception_info` through the client (2/12 on B10H, both gpt-5.4-mini).** What they do instead: read the step log files under `local_stores/<store>/logs/` (12/12), open the SQLite database with `sqlite3` and select `exception_info` from `step_run` (8/12), guess `step.logs` or `zenml pipeline runs describe` (8/12). The SQLite route only exists on the local stack; against a server the same agents would be stuck with the log files. Same docs/CLI items as B10, now with a task that measures them one tier down.
- **The typed-pipeline-parameter error fires in 8/12 B14H trials (2/6 on B14)** because agents now route three values (summary, artifact name, version) into the step and annotate the pipeline parameter. Both failed Haiku trials recovered by loading the artifact through `Client()` inside the step or passing `version.load()` as a plain parameter: the report is right, the run completes, and the step has **no recorded input** (`input_types=0`). Docs sentence to add next to the artifact-passing example: "`Client().get_artifact_version(...).load()` inside a step records no input; pass the version into the pipeline call (unannotated parameter) or use `load_artifact`."
- **The store cannot tell "by name and version" from "by id".** The step-run input carries the artifact version's id, name and number and an `input_type`; nothing records the lookup. B14H therefore grades by id and has the report cite name and version, which the grader checks against the recorded input's `artifact.name` and `version`.
- **Agents delete their own runs and change run naming when nothing forbids it.** One opus trial on B10H changed scheduled run names to `scheduled-<date>-{time}` to avoid a name clash on restore; one opus and one Haiku trial on B14H deleted their own failed `region_report` runs before re-running. Task fix: state the run-name/tag contract in B10H and check it with a hidden `--trigger scheduled` day; count `region_report` failures from the store only if the instruction forbids deleting them.
- **Cost, not pass rate, is where the frontier moved.** Claude Code opus spent 1.24M tokens median on B10H against 476k on B10 ($1.37 vs $0.58 per trial); Codex terra 392k vs 271k. B14H: opus 599k vs 284k, terra 750k vs 385k. A benchmark row that reports tokens next to pass rate keeps this signal even where pass rate is saturated.
