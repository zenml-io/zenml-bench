## 2026-09-09 — B3 stale-cache: the fault and three verified fixes (Level 0 spike)

Spike run locally on the `shared/projects/nightly` project, sequence of datasets **a, a, b, b, c** copied to `data/train.csv` between runs, each fix in its own fresh store. Statuses read back with `Client().list_pipeline_runs(pipeline="nightly_training")` and `run.steps[name].status`.

**Unfixed project** (`load_data(path: str)`): run 1 completed, runs 2–5 all `cached`, score stuck at dataset a's value (0.9111) even after b and c were copied in. Fault reproduced.

**All three fixes below produced the target pattern**: run 1 completed → run 2 cached → run 3 completed → run 4 cached → run 5 completed, with scores 0.9111 / 0.9111 / 0.7611 / 0.7611 / 0.7778, and `train` cached exactly when `load_data` was cached.

1. **Brief's reference**: uncached `content_hash(path) -> str` step whose output is passed into `load_data(path, digest)`. Works with the *default* cache policy on `load_data`.
2. `@step(cache_policy=CachePolicy(file_dependencies=["data/train.csv"]))` on `load_data`. Path is relative to the source root (the `zenml init` directory).
3. `@step(cache_policy=CachePolicy(cache_func=data_digest))` where `data_digest()` returns the file's sha256.

**Why fix 1 works despite the digest being a new artifact version every run** (this was the risk the brief flagged): ZenML's cache key uses an input artifact's *content hash* when the materializer can compute one, and only falls back to the artifact *ID* when it cannot. Observed: run 1 and run 2 produced digest artifacts with different IDs (`de213353` v1, `59f79a77` v2) but identical `content_hash`, and `load_data` got the identical `cache_key` (`9361e38dbb`) in both runs. The docs' phrase "artifact values or IDs" means values first, IDs as fallback. Built-in materializers (str, pandas DataFrame) support content hashing.

Consequences for the task: the grader's expected statuses are exactly the pattern above; `solution/solve.sh` can be fix 1 and `solution/alternatives/` gets fixes 2 and 3; `disable_train_cache.sh` and `disable_all_caching.sh` shortcuts will fail the "run 2 / run 4 cached" checks; `hardcode_score.sh` will fail the dataset-c check. Fixture scores at this pin: a=0.9111, b=0.7611, c=0.7778 (accuracy, `LogisticRegression(max_iter=1000)`, 30% test split, `random_state=0`).

Open: whether `train` being cached in run 2 relies on the pandas materializer's content hash or on the same artifact ID (the `load_data` output *was* the same artifact in run 2 because `load_data` was cached, so both would give the same answer here). Not load-bearing for B3 but worth knowing for B4 (nondeterministic step).

## 2026-09-09 — which artifact types hash by content (resolves the "open" note above)

`compute_content_hash` is implemented by the built-in materializers (str/int/float/bool/bytes/list/dict…), cloudpickle, dataclass, pydantic, uuid, structured-string. The **pandas integration materializer does not implement it**, so a DataFrame input falls back to its artifact ID in the cache key. Observed consequence: `enable_cache=False` on `load_data` alone makes `train` rerun every time (new DataFrame artifact each run), so it is **not** a valid B3 fix; it is now the `disable_load_cache_only.sh` shortcut. A fitted sklearn model *did* hash by content (`evaluate` stayed cached after `train` reran with identical data), so the model is going through a content-hashing materializer.

## 2026-09-09 — Harbor 0.22.0: what the brief got wrong, and what we rely on

Established by installing `harbor==0.22.0` (`uv tool install`) and running a hello task, then B3, with the `oracle` and `nop` agents. Corrections to brief §3.2:

- Local task dirs run with `harbor run -p <dir>`; `-t` is a registry task name. Attempts: `-k`, concurrency: `-n`, output: `-o <dir> --job-name <name>`. Harbor refuses to reuse a job dir whose `lock.json` differs; delete it first.
- The do-nothing agent is called `nop`.
- Reward: the verifier reads `/logs/verifier/reward.json` first and falls back to `reward.txt`. Extra numeric keys in the JSON become metric columns in `result.json`. So research tasks can write `{"reward": 0|1, "gap_closed": x, ...}` exactly as the brief planned.
- `tests/` is uploaded to `/tests` after the agent finishes and `test.sh` runs as the image's default user (root) from the image's `WORKDIR`. `/solution` exists only during oracle runs. In `[verifier] environment_mode = "separate"` Harbor does **not** upload tests; the verifier image must already contain `/tests/test.sh`.
- `[[mcp_servers]]` is `[[environment.mcp_servers]]`. Timeouts are per section (`[agent].timeout_sec`, `[verifier].timeout_sec`). There is no task-level `skills/` convention: skills come from `harbor run --skill <dir|org/repo@ref>` or `[environment].skills_dir` inside the image. The "+ skill" condition is therefore a run-time flag, not a task variant.
- **There is no Harbor LLM proxy.** API keys are passed into the container as env vars. Under `no-network` the agent cannot reach its model. The documented pattern is `[environment] network_mode = "no-network"` plus `[agent] network_mode = "allowlist"` / `allowed_hosts`, or `--allow-agent-host api.anthropic.com` at run time (agent phase only). Agent *installation* happens in the setup phase under the baseline policy, so the image must pre-install the agent or its dependencies.
- **Blocker on this Mac:** Docker Desktop's VM kernel lacks `CONFIG_NFT_FIB_INET`, which Harbor's egress sidecar needs, so `no-network` and `allowlist` are rejected outright. Only `public` runs locally. Options: OrbStack/Colima as the Docker runtime on macOS, or run restricted-network tasks on Linux CI / Modal / Daytona. `task.toml` says `public` until this is decided.
- Base image now pre-installs `nodejs npm procps` (claude-code, codex), `ripgrep` (codex), `tmux` (terminus-2) so agent setup does not need network.
- Harbor builds the task image with `environment/` as the build context, so a task must be self-contained. `scripts/sync_project.sh <project> <task>` copies `shared/projects/<project>` into `environment/<project>`; the copy is committed (Harbor registry pulls task dirs) but `shared/projects/` stays the source of truth.
- Job output: `jobs/<job>/<task>__<id>/{result.json, trial.log, agent/, verifier/}`; the reward is at `result.json` → `verifier_result.rewards.reward`. LLM agents write `agent/trajectory.json` in ATIF format (Harbor RFC 0001); `analyse_trajectories.py` parses that.
- B3 through Harbor: oracle 1.0, nop 0.0 (matches `grade_local.sh`).

## 2026-09-09 — B7 kubernetes-settings: how to grade Kubernetes config with no cluster (tier C1)

- On a local stack ZenML **drops** orchestrator settings that don't belong to the active orchestrator's flavor at compile time (warning "Not including stack component settings with key …"), whether keyed `orchestrator` or `orchestrator.kubernetes`. They never reach the run record. Resource settings *are* recorded (with a warning that the local orchestrator ignores them). So the run record cannot be the grader.
- Registering a Kubernetes orchestrator against the local SQLite store works (warning only: "component running remotely while connected to the local database"). The task image registers `k8s` (flavor kubernetes), `reg` (default container registry) and `k8s-stack`; the active stack stays `default`.
- Grader = dry-run compile: import `pipeline.training_pipeline`, apply `config.yaml` the way `run.py` does (`pipe._parse_config_file(...)` → `PipelineRunConfiguration`, plus `with_options(config_path=...)`), `pipe.prepare()`, then `Compiler().compile(pipeline, stack=Stack.from_model(Client().get_stack("k8s-stack")), run_configuration)`. In the compiled deployment the settings key is renamed to `orchestrator:<component-name>` (`orchestrator:k8s`), stored as a generic `BaseSettings`; re-validate with `KubernetesOrchestratorSettings.model_validate(raw.model_dump())`.
- Pipeline-level `pod_settings` are merged into every step at compile, so "only `train` gets the GPU" is checked by asserting the other steps have none.
- `ResourceSettings.memory` rejects Kubernetes quantities like `8Gi` (`SettingsResolvingError`) and wants `8GB`; `KubernetesPodSettings.resources` takes `8Gi`. Both forms are accepted by the grader (the orchestrator honours both). Kept as a realistic trap; the instruction says "8Gi".
- Base image now installs the `kubernetes` client (needed by the settings classes).

## 2026-09-09 — B7 correction: `pod_settings.service_account_name` is a dead field

`KubernetesPodSettings` has no `service_account_name` field. ZenML's settings models accept unknown keys silently, so `pod_settings: {service_account_name: …}` validates, shows up in `model_dump()`, and is never read: `build_pod_manifest` takes `service_account_name` from `KubernetesOrchestratorSettings.step_pod_service_account_name or .service_account_name` (entrypoint line ~526), and `add_pod_settings` applies node selectors, resources, tolerations etc. but no service account. The first B7 reference and grader both used the dead field; every agent in the first baseline used `step_pod_service_account_name` (found by reading ZenML's source under site-packages, since neither the docs snapshot nor the skill mentions it) and was marked wrong. Fixed: reference and `code_settings.sh` use `step_pod_service_account_name`; grader accepts `step_pod_service_account_name` or the top-level `service_account_name` (which the orchestrator-pod check then rejects); `dead_field_service_account.sh` is a shortcut that must score 0. Also `ResourceSettings.memory` accepts `8GB`, `8GiB`, `8192MB`; rejects `8Gi`, `8G`.

Lesson for authoring: a reference solution must be checked against the code path that consumes the setting, not only against "does it validate". Settings that validate are not settings that work.

## 2026-09-09 — R1 research loop: where the project lives and what the Model Control Plane records

- The brief's `envs/research/` is `shared/projects/research/`, like every other project; `scripts/sync_project.sh research tasks/r1-improve-within-budget` copies it. `make_data.py` (excluded from the sync) regenerates `data/train.npz`, `data/val.npz`, the grader's `tests/fixtures/hidden.npz` and `expected.json`. Tabular scikit-learn was chosen over a character-level LM; measurements and the reason are in `docs/research-noise.md`.
- **Attaching runs to a model version.** `research.with_options(model=Model(name="research_model", version="<config name>"))(...)` creates the version on the first run and *reuses* it on later runs with the same name: observed one version `baseline` with two linked runs (seeds 0 and 1) and two `model` artifacts (versions 1 and 2). `mv.pipeline_runs` (hydrated) lists them; `mv.model_artifacts["model"]` maps artifact-version number to the artifact.
- **Which artifact "is" the version's model.** `mv.get_model_artifact("model")` returns the most recently produced one. The grader does the same but only among artifacts a completed run produced (see below).
- **Metadata on the version is last-writer-wins.** `log_metadata({"val_log_loss": x}, infer_model=True)` inside `evaluate` writes to the model version's `run_metadata`; a second run on another seed overwrote it (0.6584 became 0.6603). Per-run values survive as each run's `evaluate` step output (`run.steps["evaluate"].outputs["val_log_loss"][0].load()`), which is what the grader and the README read. Data outputs of a *cached* `prepare_data` are still linked to the version as data artifacts.
- **Promotion.** `mv.set_stage("production")` raises `RuntimeError` if another version already holds the stage unless `force=True`; with force the previous production version becomes `archived`. `Client().get_model_version("research_model", "production")` (or `ModelStages.PRODUCTION`) returns the current one and raises `KeyError` when the stage is empty. CLI: `zenml model version update research_model <name> --stage production --force`. `zenml model version list --model research_model` shows numbers and stages but not names.
- **Telling a run-produced artifact from a hand-saved one.** `save_artifact(...)` gives `producer_step_run_id = None` and `save_type = manual`; a step output has `producer_step_run_id` pointing at the `train` step run, whose `pipeline_run_id` must be among the version's `pipeline_run_ids`. `zenml.model.utils.link_artifact_version_to_model_version` attaches any artifact to any version, so "linked to the production version" alone is not evidence; the grader requires the chain artifact → producer step run (`train`, status completed) → run linked to the version. Shortcuts `promote_unverified.sh` and `promote_unverified_with_run.sh` exercise both halves.
- **Anchors.** `gap_closed` uses seed-0 hidden log loss of the baseline (0.6585) and the reference (0.4581), computed by `make_data.py` with the project's own `build_model` on `prepare.subsample(..., seed=0)`, so the oracle (one run of the reference config on seed 0) scores exactly 1.0 and a run on another seed lands within a few hundredths. The sklearn `SklearnMaterializer` is what the store records for the model artifact; `.load()` in the verifier process returns the fitted estimator.
- **B9 trap hit again:** `return prepare.load_data()` from a step annotated with a four-way `Tuple` fails with "Unable to unpack step artifact"; the step must `return a, b, c, d` literally.

## 2026-09-09 — B10 why-did-it-fail: where ZenML 0.96.4 records a failed step, and how the history is produced

Spiked on `shared/projects/daily_report` in fresh stores (`ZENML_CONFIG_PATH`), every failure produced by really running the pipeline.

- **The traceback lives on the step run, not the pipeline run.** `Client().get_pipeline_run("scheduled-2026-09-09").steps["parse"].exception_info` is an `ExceptionInfo` with `traceback` (user frames only), `source` (`builtins.ValueError`), `message` (`could not convert string to float: '1,234.50'`) and `user_code_line`. `run.exception_info` is `None` for a step failure (it is for orchestration-level failures). The full traceback, ZenML frames included, is also in the step's log file: `step.resources.log_collection[*]` are `LogsResponse`s with `.uri` pointing at `local_stores/<store>/logs/<id>.log` (JSON lines, one per log record; sources `prepare_step` and `step`).
- **When a step raises, the run is `failed` and downstream steps get no step-run record at all.** `run.steps` for the 09-09 run is `{"load": completed, "parse": failed}`; `summarise` and `write_report` are simply absent. An agent that looks for "which step failed" must look at the *last* step present, not for a step with status failed among four.
- **The CLI cannot show any of this.** `zenml pipeline runs` has `list`, `delete`, `refresh`, `resume`, `retry`, `stop`, `wait-conditions`; there is no `describe`. `zenml pipeline runs list --output json` gives `id`, `index`, `run_name`, `pipeline`, `status`, `stack`, `owner` and nothing about steps. Filters `--tags scheduled --status failed --name startswith:scheduled` work. So the CLI finds *which* run failed; the Python client (or the log file) is needed for *why*. This asymmetry is the teaching point of the task.
- **Scheduled vs manual runs.** `run.py --trigger scheduled` sets `with_options(run_name=f"scheduled-{date}", tags=["scheduled"])`; manual runs get `run_name=f"manual-{date}-{{time}}"`, tags `["manual"]`. Both are recorded: `list_pipeline_runs(tags=["scheduled"])`, `name="startswith:scheduled"` and the CLI equivalents return exactly the scheduled runs. Run names are unique per project: a second `scheduled-2026-09-08` raises `EntityExistsError` *before* any run is created (the message suggests `{date}`/`{time}` placeholders). An agent that re-runs the failed day with `--trigger scheduled` hits this; the plain `--date` re-run is named `manual-2026-09-09-<time>`.
- **History is built at image build by `environment/setup_store.sh`** (13 s): 09-05 `FileNotFoundError` in `load` (no export delivered), 09-06 `FileNotFoundError` in `write_report` (`reports/` missing, then created by the script), 09-07 and 09-08 completed, 09-09 `ValueError` in `parse` (the real fault), then a manual `--date 2026-09-31` typo run so the most recent failure is a distractor. The script writes a manifest (`seed_runs.json`: ids, names, statuses, step statuses) next to the store: `$ZENML_CONFIG_PATH/seed_runs.json` when that variable is set (as `grade_local.sh` does), else `/var/lib/zenml-bench/seed_runs.json` (image). The grader checks the seeded runs by name and status regardless, and by id when the manifest is present. Known limitation: all seeded runs carry the image-build timestamp, minutes apart, not a week apart; the instruction says "this morning" and relies on names/tags rather than timestamps.
- **Re-running the fixed pipeline for 09-09 leaves `load` CACHED** (same code, same `date` parameter; the file is not part of the key) and `parse` executes. The grader therefore identifies the target run by `steps["load"].config.parameters["date"]` and by its `summarise` output, never by run name or cache status.
- **Grader (six tests):** completed run with date 2026-09-09 and the reference summary; the grader runs the agent's entrypoint on two hidden exports (separator amounts in other rows/regions; and one with none, because `df["amount"].str.replace(...)` fails on a float column and would break every normal day), after expiring all step runs as cache candidates; seeded runs untouched; `data/2026-09-09.csv` hash unchanged; only `daily_report` registered. Metrics: `agent_runs`, `agent_failed_runs`, `agent_runs_for_target`, `seeded_runs_seen`. Local results: oracle 1, noop 0, six shortcuts 0 each on the check built for it, three alternatives 1.

## 2026-09-09 — R2 and R1-bare: evidence rules, and what a repeated seed does

- **A repeated seed produces no new evidence.** `same_seed_thrice.sh` runs the reference config three times on seed 0: runs 2 and 3 are full cache hits (`prepare_data`, `train`, `evaluate` all CACHED), the cached `train` output is run 1's artifact, whose `producer_step_run_id` is run 1's step. The grader's chain (artifact → producer step run → linked run) therefore counts one backed run and one seed even though the version lists three runs. Nothing special was needed to defeat this shortcut; it falls out of "grade the producer chain, not the link table".
- **R2 threshold.** Mean recorded `val_log_loss` over the backed runs must be ≤ 0.56 (baseline mean 0.659, so a margin of 0.10; logistic C=1 at 0.64 fails it, any ensemble passes). Stated in the instruction. `edit_evaluation.sh` passes this rule with a fake 0.01 and still scores 0 on the hidden data, which is why the hidden-data check stays in R2.
- **R1-bare evidence.** With no store, "backed by a run" becomes "byte-identical to a `model_path` file named in a `results.tsv` row" (sha256). `trim_results.sh` (13 runs, then delete rows to look within budget) scores 0 because the deleted row was the promoted model's; an agent that deletes *other* rows would pass the budget check, so the bare budget rule is weaker than the store's and is noted as such in `results/level3-r1.md`.
- `grade_local.sh` works unchanged for the bare task: it runs `zenml init` in the copy, which the bare project ignores.

## 2026-09-09 — B14 artifact-retrieval: feeding a historical artifact version into a new pipeline

Spiked on the B10 store. Everything below was observed with `Client()` after real runs.

- **An artifact version can be passed straight into a pipeline call** (`region_report(summary=Client().get_artifact_version(id))`) and ZenML records it on the step run as an input with `input_type == "external"` and the same artifact version id (`run.steps[name].inputs[arg]` → `StepRunInputResponse`, fields `input_type`, `index`, `chunk_index`, `chunk_size` on top of the artifact version). **But only if the pipeline function's parameter is untyped or `Any`.** A parameter annotated `dict[str, Any]` fails at `prepare()` with "Only JSON serializable inputs are allowed as pipeline inputs": typed pipeline arguments are validated as JSON parameters, and an `ArtifactVersionResponse` is not one. A step parameter can stay typed (`summary: dict[str, Any]`), because the step receives the loaded value.
- **`load_artifact(<version id>)` inside a step is recorded too**, as an input named after the artifact (`daily_report::summarise::output`) with `input_type == "manual"`. So both routes leave lineage, and the grader accepts either by matching the artifact version id across all recorded inputs regardless of type.
- **A cached step run keeps its recorded inputs** (second identical `region_report` run: step `cached`, inputs still list the historical version). `solve_then_run_twice.sh` guards this.
- **Tags can be added to an existing run**: `zenml.utils.tag_utils.add_tags(tags=["backfill"], run=<id>)`; `run.tags` then lists both `manual` (from the run) and `backfill`. `setup_store.sh` uses this to mark the backfill runs after the fact so `run.py` (shared with B10) is unchanged.
- **Lookup by name and version works for step outputs**: `Client().get_artifact_version("daily_report::summarise::output", 4)` returns the same id as the run's output; the auto-generated name is `<pipeline>::<step>::<output>`.
- **History** (`environment/setup_store.sh`, ~25 s): four backfill days run by hand with exports copied from `environment/backfill/` (2026-08-24, 08-25 completed; 08-26 failed in `write_report` because `reports/` was moved aside, so its summary artifact exists and has the largest total of all; 08-27 completed and is the answer; 08-28 has no export, fails in `load`), tagged `backfill`, then the cron week (09-05 missing file, 09-06/07/08 completed, 09-09 the separator fault, a manual typo run). Completed scheduled 09-08 (22.4k) beats every backfill day (max 16.5k), and 08-25 (16.2k) is within 300 of the answer, so the tag, the status and an actual comparison are each load-bearing. The grader derives the correct artifact version from the store the same way (ids differ per build) and checks the fixture's date as a sanity check.

## 2026-09-10 — "+ MCP" condition: how the ZenML MCP server connects, and what Harbor does with it

Spiked by running `zenml-io/mcp-zenml` (commit `33c6c7f`, v1.2.0, pushed 2026-09-08) over stdio against a fresh B10 store (`ZENML_CONFIG_PATH`), driven by a small `mcp` client script, then inside the task image through Harbor.

## 2026-09-10 — R1/R2/R1-bare: the training-slice rule is now checked from the record ("if you want to check it, make the pipeline record it")

- **The gap.** The instruction said "train on `prepare.subsample(X, y, seed)`", but the store only held the fitted model, so the grader could not tell a slice-trained model from one trained on all 3000 rows (which scores 0.371 hidden against the honest reference's 0.458; `docs/research-noise.md`). The pilot could only read trajectories for it.
- **The fix is two more outputs, not a cleverer grader.** `train` now returns `(model, n_train_rows, train_rows_digest)`; the digest is `prepare.digest(X, y)` = sha256 of the raw rows (float32 X bytes + int64 y bytes) taken right after `subsample`, before any feature engineering. Observed in a fresh store: `run.steps["train"].outputs` has three keys, each artifact's `producer_step_run_id` is the `train` step run, the `int` and `str` go through the built-in materializers, and the model version's `data_artifacts` lists the two new artifacts next to `val_log_loss`. So the grader walks the chain it already walked (production version → completed `research` run → `train` step → outputs) and reads the evidence next to the model. Nothing about promotion or caching changed.
- **What the grader checks, per backing run** (`verify.slice_violation`): recomputes the seed's slice with its own copy of the training data (`tests/fixtures/train.npz`, written by `make_data.py --fixtures-dir`) and its own frozen copy of the subsample rule; rejects if `n_train_rows` exceeds the slice size (1050), or equals it with a digest that is not the seed's, or the outputs are missing. Fewer rows are fine (outlier dropping is a legitimate technique; `feature_engineering_in_train.sh` is the alternative that guards this). New shortcuts `train_on_full_set.sh` (3000 rows, hidden 0.37 → 0) and `resample_from_full_set.sh` (1050 rows from the agent's own RNG → digest mismatch → 0). Metrics `max_train_rows` and `slice_violations` are recorded per trial.
- **R1-bare gets the same rule through `results.tsv`**: `train.py` writes `n_train_rows` and `train_rows_digest` columns and the grader checks the promoted model's row the same way. It is enforceable to the same degree as the ZenML variant: in both, agent-controlled code writes the record, so an agent can only pass by deliberately falsifying it rather than by ignoring the rule. The difference is where the record lives (a step output tied to the artifact by `producer_step_run_id`, versus a TSV column next to a file hash), not how strong it is.

## 2026-09-10 — the with/without-ZenML comparison: why the budget is a stated wall clock, not a compute cost

Three designs were measured before choosing (`OMP_NUM_THREADS=1`, the reference gradient-boosting config, 35% slices):

- **Bigger data so a fit costs ~60 s.** Rejected by measurement: `HistGradientBoostingClassifier` bins features once and then fits in 1.2 s on a 21,000-row slice (60,000 training rows, 60 features) and 3 s on 42,000 rows; only random forests (18 s) and kernel SVMs get expensive. The strongest family stays cheap, and at 21k rows the seed-to-seed spread collapses to ±0.0005, which removes the noise the task is about. It would also put ~100 MB of data into git or force a generator-at-load-time project that differs from R1.
- **A sleep or extra work inside `train`.** Rejected: anything inside the step is bypassed by the off-loop scripts every pilot trial used (`import prepare; prepare.subsample(...)` and fit in plain Python), so it taxes the honest agent only.
- **A stated wall clock, enforced by Harbor.** Chosen. The pilot's timing rows show where the time went: opus's first official run came at minute 18–36 in the ZenML variant and never in 5/6 bare trials, with 10–47 off-loop scripts before it; the machine's fits were seconds. The scarce resource is the agent's own tool-call latency, so the clock binds by itself. `tasks/r1-clock-improve-within-budget` and `tasks/r1-bare-clock-improve-within-budget` copy the R1/R1-bare tasks (same project, data, grader, 12-run rule) and add one rule: 25 minutes counted from the first action, the harness stops you and grades what is promoted (`[agent] timeout_sec = 1500`), plus `[environment] cpus = 2` so a sweep cannot take 18 cores and the host machine stops being a variable (Harbor maps `cpus` to Docker's CPU limit). Telling the agent the clock exists is the point: the pilot agents did not know there was a 40-minute limit and could not plan for it. The original R1/R1-bare tasks are unchanged so the earlier baselines stay comparable.
- Confound that stays: the ZenML variant pays a few seconds of client overhead per official run, and that is part of "with ZenML". Trials run with `-n 1` so they never share the machine.

## 2026-09-10 — B11 stack-registration: what registers offline, how a connector link is recorded, and where the active stack lives

Spiked in fresh stores with `Client()` and the CLI; then confirmed in a sealed container (`docker run --network none`).

- **The `aws` connector type does not exist until the AWS integration packages are installed** ("Service connector type aws not found"). The base image has none; the task Dockerfile adds `s3fs`, `boto3`, `aws-profile-manager` (the `s3` integration's requirements; `sagemaker` is not needed for the connector). Same packages added to `.venv` for `grade_local.sh`.
- **`zenml service-connector register --type aws …` verifies the credentials against AWS STS unless `--no-verify` is given.** Sealed: "Could not connect to the endpoint URL: https://sts.eu-central-1.amazonaws.com/", ~11 s. With network and fake keys: `InvalidClientTokenId`. `--no-verify` registers without any call. The docs snapshot has zero mentions of `--no-verify` (only `zenml login --no-verify-ssl`); `--help` shows it, and every Claude Code baseline trial found it there.
- **`zenml artifact-store register … --connector X` always verifies** (`no_verify=False` is hardcoded in `generate_stack_component_register_command`): the store is created, the verification error is printed, and the link is simply absent. The link is made without a call by `zenml artifact-store connect <store> --connector X [--resource-id <bucket>] --no-verify`, or by `Client().update_stack_component(name_id_or_prefix=…, component_type=…, connector_id=…, connector_resource_id=…)`; `create_stack_component()` takes no connector at all.
- **How the link is recorded:** `ComponentResponse.connector` (the connector response, `.id`/`.name`) and `ComponentResponse.connector_resource_id`. The CLI `connect` without `--resource-id` fills the resource id from the store's `path` (`s3://ml-platform-artifacts/zenml`, via the flavor's `resource_id_attr="path"`); with `--resource-id ml-platform-artifacts` it records exactly that; the Python route records whatever it was handed, or `None`. A connector scoped with `--resource-type s3-bucket --resource-id <bucket>` carries `resource_id` itself. The grader computes an *effective bucket* = first path segment of (component resource id or connector resource id) and requires `ml-platform-artifacts`; a link with neither (Python route, no `connector_resource_id`) is the `link_without_bucket.sh` shortcut.
- **Secrets are readable by the grader:** `Client().get_service_connector(name, expand_secrets=True).configuration` holds `SecretStr`s for `aws_access_key_id`/`aws_secret_access_key`; `.get_secret_value()` returns the placeholder. Without `expand_secrets` only `region` is visible.
- **The active stack is per repository.** `zenml init` writes `.zen/config.yaml` with `active_stack_id`; `zenml stack set` inside that directory updates it ("Active repository stack set to"), outside it updates only the global config (`$ZENML_CONFIG_PATH/config.yaml`). `Client()` is a singleton bound to the repository found at first use, so the grader reads `Client(root=APP_DIR).active_stack_model` and `test.sh` runs from the project; `global_active_only.sh` is a shortcut. Metric `global_active_too` records whether the agent set both.
- **`ZENML_ACTIVE_STACK_ID` overrides both** for one process; the grader uses it to run `run.py` on the default stack without touching the agent's choice, and the run record shows `stack: default`.
- **The default stack and components are immutable at this pin:** `zenml stack delete default` → "The default stack cannot be deleted"; rename/update → "The default stack cannot be modified"; `zenml artifact-store delete default` → "The default artifact_store cannot be deleted". The brief's `delete_default.sh` shortcut is therefore impossible; the grader keeps the "default intact" test as a cheap guard for future pins.
- **A Kubernetes stack without a container registry fails validation only at run time** (`StackValidationError: Missing stack components {container_registry}` from `python run.py`); `stack register` and `stack set` accept it. The task therefore includes `ecr-prod`. The `aws` container-registry flavor rejects a `/` in the URI ("Property `uri` can not contain a `/`"), the `default` flavor accepts anything, so the task's URI is the bare ECR domain and both flavors are accepted.

## 2026-09-10 — B4 nondeterministic-step: which cache policies make a step rerun

Spiked on `shared/projects/sampling` (`load_events` sleeps 3 s and reads `data/events.csv`; `sample_events(events, n)` is `df.sample(n)`; `review_report` summarises). Two runs with the same `n` in each fresh store:

- Unfixed: run 2 has all three steps `cached` and the same `review_sample` artifact version. Fault reproduced.
- `@step(enable_cache=False)` on `sample_events` only: run 2 `load_events` cached, `sample_events` completed, `review_report` completed (its input is a new DataFrame artifact and pandas has no content hash, so it reruns by itself). Reference.
- `CachePolicy(cache_func=<function returning uuid4().hex>)` on the sampler: same pattern. Alternative.
- A `nonce: float` step parameter drawn with `random.random()` in the pipeline function: same pattern (parameters are in the cache key). Alternative.
- **`CachePolicy(expires_after=0)` does nothing** (run 2 all cached); `expires_after=1` works (a rerun seconds later misses). `0` is treated as unset. Shortcut `expires_after_zero.sh`; `expires_after_one.sh` is accepted as an alternative on outcome.
- Grader runs `python run.py --n 37` twice (an `n` the agent has not used, so run 1 is a fresh key whatever the fix and nothing is asserted about its statuses), then asserts run 2: `load_events` CACHED, `sample_events` COMPLETED, both samples are sets of real `event_id`s of size `n` and differ, and each `review_report` matches its own run's sample.

## 2026-09-10 — B6 model-promotion: what a run records about its model version, and the cache-across-promotion trap

Spiked on `shared/projects/model_promotion` (versions 1 linear `val_mae` 4.857, 2 forest 5.971, registered by `@pipeline(model=Model(name="demand_forecaster"))` with `log_metadata({"val_mae": …}, infer_model=True)`; the inference pipeline is configured with `Model(name=…, version="latest")`).

- `ArtifactConfig(artifact_type=…)` wants the `ArtifactType` enum (`ArtifactType.MODEL`), not the string `"model"`.
- `mv.run_metadata["val_mae"]` is a plain float at this pin (not a wrapper with `.value`). `mv.model_artifacts["model"]` maps artifact-version number → response; `mv.get_model_artifact("model").load()` returns the estimator.
- **A run records the version its `Model` resolved to** (`run.model_version.number`; also on `step.model_version`). `version="latest"` resolves at run time to the newest version; `version="production"` / `ModelStages.PRODUCTION` to the staged one.
- **The model version is not part of the step cache key** (`cache_utils.generate_cache_key`: code, parameters, input artifacts, outputs, environment, secrets, cache policy extras). Observed: after promoting version 1, changing only the pipeline's `Model(version="production")` and rerunning on the same batch gives a run *linked to version 1* whose `predict` is CACHED from the version-2 run, predictions included. Lineage says one thing, predictions another. `stage_without_cache_fix.sh` is that shortcut; the grader always compares a run's predictions with its linked version's own model on the run's own batch.
- Fixes that work across a promotion flip (same input both times): `enable_cache=False` on `predict` (reference); the model artifact fetched in the pipeline function (`Client().get_model_version(name, ModelStages.PRODUCTION).get_model_artifact("model")`) and passed to `predict` as an input, recorded as an input of type `lazy` with the artifact's id, so the cache key follows the artifact (cleanest lineage); `CachePolicy(cache_func=<production version id>)`.
- Grader sequence: production == lowest `val_mae` over all versions; some completed `batch_forecast` run is linked to it *and* its predictions equal that version's model on the run's own `batch` artifact; grader run on a hidden batch; grader promotes the worst version with `force=True` and reruns on the same hidden batch, predictions must now be that version's (defeats `hardcode_version.sh` and the cache trap). Seeded versions (manifest `seed_versions.json` written by `setup_store.sh`, ids and `val_mae`) must be unchanged and no new versions trained.

## 2026-09-10 — B14H artifact-retrieval-hard: supersession, and what a step input does not record

- **The criterion is stated as a business rule** ("the most recent processing that completed is the one that counts for that day; the busiest day is the one whose counting summary has the largest total") and the history makes every simpler rule pick a different run. `setup_store.sh` runs the four backfill days, then re-processes three of them with corrected exports (`environment/backfill/<date>.v2.csv` copied over the same name). Totals from the seeded store: 08-24 12.2k; 08-25 16.2k completed, re-processed 17.0k **failed** in `write_report`; 08-26 17.2k **failed** in `write_report`, re-processed 16.4k completed; 08-27 16.7k completed, re-processed 15.0k completed; scheduled 09-08 22.4k. Right rule → 08-26 second pass (v5). Largest completed backfill total → 08-27 first pass (v4, superseded). Largest backfill summary of any status → 08-26 first pass (v3). Latest per day ignoring status → 08-25 second pass (v6). Ignore the tag → 09-08 (v10). Each is a shortcut.
- **Re-processing a day needed the cache expired first.** `load(date)` is cached on code + `date`, not on the file, so copying a corrected export over `data/2026-08-26.csv` and re-running would have served the *old* DataFrame from cache and produced an identical summary. `setup_store.sh` calls `Client().update_step_run(id, cache_expires_at=now)` on every step run before the second pass, the same call the graders use. This is the B3 fact used to *produce* history rather than to grade it.
- **Name + version lookup is not distinguishable from lookup by id in the store.** `Client().get_artifact_version("daily_report::summarise::output", "5")` returns the same id as `run.steps["summarise"].outputs["output"][0]`; `version` is a string (`'5'`). The step-run input record holds the artifact version (its id, name, version) and `input_type` (`external` when passed into the pipeline call, `manual` when loaded with `load_artifact` inside the step); nothing records how the caller obtained the version object. So the grader matches the version id as B14 does, and the instruction instead requires the report to cite `artifact_name` and `artifact_version`, which the grader checks against `version.artifact.name` and `version.version` of the run's recorded input. `load_artifact(name, version)` inside the step also works (`load_artifact_in_step.sh`).
