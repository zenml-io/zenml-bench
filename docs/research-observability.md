# Observability into Harbor rollouts (research notes, 2026-09-10)

Question: how do people see what an agent did inside a Harbor task container, and what could this repo adopt cheaply? Sources are Harbor 0.22.0 as installed at `~/.local/share/uv/tools/harbor/lib/python3.14/site-packages/harbor/` (called `$H` below), this repo's `jobs/` output, and primary docs. Terms defined inline on first use.

## 1. What Harbor writes per trial

A *trial* is one attempt of one agent at one task. `harbor run -o jobs --job-name <name>` creates `jobs/<name>/` holding `config.json`, `result.json`, `job.log`, `lock.json`, and one directory per trial named `<task>__<6 random chars>`. Observed in `jobs/baseline-b10-why-did-it-fail-claude-code-bare/`.

Each trial directory has this layout (source: the docstring in `$H/models/trial/paths.py` and the observed job above):

- `config.json` and `result.json`: the trial's settings and outcome. `result.json` holds `agent_info` (name, version, model), `agent_execution` (`started_at`/`finished_at`), `verifier_result.rewards` (the whole `reward.json`, so extra metrics ride along), `exception_info` and `step_results`.
- `agent/`: the mounted `/logs/agent` from inside the container. For claude-code it contains `trajectory.json` (ATIF, see below), `claude-code.txt` (the raw stream-json stdout of the `claude -p` process, one JSON event per line, starting with a `system/init` event that lists tools and MCP servers), `setup/` (install logs), and `sessions/`, which is the whole `CLAUDE_CONFIG_DIR` the agent ran with. That last one matters: `$H/agents/installed/claude_code.py:1838` sets `CLAUDE_CONFIG_DIR` to `/logs/agent/sessions`, so Claude Code's own native session log lands at `agent/sessions/projects/<cwd-slug>/<session-id>.jsonl` and is kept alongside the ATIF file. In the sample trial the three files are 164 KB (stdout), 219 KB (ATIF) and 186 KB (native session).
- `verifier/`: `reward.json`, plus whatever the task's `test.sh` writes there (`pytest.log`, `junit.xml`, `test-stdout.txt`, `metrics.json` for this repo).
- `artifacts/`: files the task copied to `/logs/artifacts` inside the container, plus `manifest.json`. Docs: https://www.harborframework.com/docs/run-jobs/results-and-artifacts. Extra paths can be pulled with `harbor run --artifact <container path>`.
- `trial.log`: Harbor's own log of the trial lifecycle.

### ATIF, the trajectory format

ATIF (Agent Trajectory Interchange Format) is Harbor's JSON schema for "what happened in an agent run". The spec is an RFC in the Harbor repo (https://github.com/harbor-framework/harbor/blob/main/rfcs/0001-trajectory-format.md), the docs page is https://www.harborframework.com/docs/agents/trajectory-format, and the Pydantic models the installed 0.22.0 uses are in `$H/models/trajectories/`. The installed models accept `ATIF-v1.0` to `ATIF-v1.7` and default to v1.7 (`trajectory.py:15-24`); the upstream spec has since added v1.8 (audio content). Our trajectories are v1.7.

The structure, from `$H/models/trajectories/*.py`:

- Root: `schema_version`, `session_id`, `trajectory_id`, `agent` (name, version, model_name, optional `tool_definitions`), `steps`, `final_metrics`, optional `notes`, `extra`, `continued_trajectory_ref`, and `subagent_trajectories` (embedded trajectories for sub-agents, v1.7).
- Step: `step_id` (1-based, must be sequential), `timestamp`, `source` (`system`|`user`|`agent`), `message` (text or a list of text/image parts), `reasoning_content`, `tool_calls`, `observation`, `metrics`, `llm_call_count`, `is_copied_context`, `extra`. Only `agent` steps may carry `tool_calls`, `metrics` or `reasoning_content` (validator in `step.py:105-121`).
- ToolCall: `tool_call_id`, `function_name`, `arguments` (dict), `extra`. Observation: a list of results, each with `source_call_id` pointing back at a tool call in the same step, `content`, and optional `subagent_trajectory_ref`. The root validator rejects results that point at an unknown call id (`trajectory.py:161-183`).
- Metrics per step: `prompt_tokens`, `completion_tokens`, `cached_tokens`, `cost_usd`, and for training use `prompt_token_ids`, `completion_token_ids`, `logprobs`. `final_metrics` sums these and adds `total_steps`.

A real claude-code step from the sample trial: `source: agent`, one `Bash` tool call with `command` and `description` arguments, and one observation carrying the command's stdout; `extra.raw_arguments` and `extra.tool_use_name` are Harbor's additions. `final_metrics.extra` holds cache creation and read counts and `service_tiers`.

Which agents emit it: `grep SUPPORTS_ATIF $H/agents` finds 31 agent classes set to `True`, including claude-code, codex, gemini-cli, cursor-cli, copilot-cli, opencode, openhands, mini-swe-agent, swe-agent, goose, and Harbor's own terminus-2. The `oracle` and `nop` agents do not (they run a shell script, so there is no model conversation). For claude-code the conversion runs after the agent exits (`populate_context_post_run`, `claude_code.py:1593`) by reading the native session jsonl; for codex it reads the `rollout-*.jsonl` file (`codex.py:55`). Validate a file with `python -m harbor.utils.trajectory_validator trajectory.json` (docs page above; module at `$H/utils/trajectory_validator.py`).

What this means for `scripts/analyse_trajectories.py`: it already consumes exactly the right two files (`result.json` and `agent/trajectory.json`), and the fields it reads (`steps[].tool_calls[].function_name/arguments`, `observation.results[].content/source_call_id`, `final_metrics`) are stable spec fields, not agent-specific ones. The one thing it cannot see is anything in `claude-code.txt` or the native session that Harbor drops during conversion, such as Claude Code's own `permissionMode`, slash command list, and MCP server list in the init event.

## 2. Built-in viewers and analysis in Harbor 0.22.0

Harbor ships a web viewer. `harbor view <folder>` starts a local FastAPI server (`$H/viewer/server.py`, 2978 lines) that scans a jobs folder and serves a prebuilt React bundle from `$H/viewer/static/` (`index.html`, `assets/`, `fonts/` are present in the installed package, so no `bun` build is needed unless you pass `--build`; `$H/cli/view.py:55-89`). I ran `harbor view jobs --no-build --port 8091` against this repo and it came up in a few seconds; `/api/jobs` listed our jobs with per-eval metrics (including this repo's extra `gap_closed`, `hidden_log_loss` and so on, because it reads `reward.json` through `result.json`), and `/api/jobs/<job>/trials/<trial>/trajectory` returned the ATIF file.

What the server exposes per trial (route names in `server.py`, lines 2411-2904): the `TrialResult`, the trajectory, an `interaction` view, `verifier-output`, a file browser (`files`, plus `files/{path}` to read any file in the trial dir), `artifacts`, `agent-logs`, and a terminal `recording` if the agent produced one. Per job: filters, a task-by-task table, a `compare` grid across agents and models (`/api/compare`, line 1796), a `summarize` endpoint that runs an LLM analysis, and `upload` to Harbor Hub. There is also a "run" tab that can launch new jobs from the browser (`/api/run`, line 1215). `harbor view --tasks` switches to browsing task definitions instead.

`harbor analyze <trial or job dir>` (`$H/analyze/analyzer.py`) is the LLM-judge companion: it spins up a container per trial, gives an agent (default claude-code with claude-haiku-4-5) the trajectory plus a rubric, and writes a structured verdict. The built-in rubric checks `reward_hacking` and `task_specification`; `--rubric` takes your own TOML/YAML/JSON, `--failing` restricts to failed trials. The viewer's "summarize" button calls the same code. For this repo this is a cheap way to ask "did the agent bypass ZenML?" across a whole baseline without reading 19-step trajectories by hand.

`harbor trial handoff <trial dir>` (`$H/cli/trials.py`, help text) resumes a finished trial's agent session in your local agent CLI. For claude-code it locates the single session jsonl under `agent/sessions/projects/` (`claude_code.py:205-215`) and opens it, so you can continue the conversation the agent had, which is a debugging tool that no external viewer gives you.

`harbor traces export --path <dir> [--sharegpt] [--push --repo org/name]` (`$H/cli/traces.py`) turns trial directories into a Hugging Face dataset, optionally in ShareGPT conversation format. That is a training-data path, not a viewer, but it shows ATIF is meant to be converted.

`harbor upload <job dir>` pushes a job to Harbor Hub (`https://hub.harborframework.com`, `$H/constants.py:12`), private by default, with `--public` and `--share-org`/`--share-user`. Harbor Hub is what the Terminal-Bench 2.1 leaderboard uses: submissions must run `harbor run ... --upload --public` so maintainers can read the trajectories (https://github.com/harbor-framework/terminal-bench-2-1). The 2.0 leaderboard at https://www.tbench.ai/leaderboard/terminal-bench/2.0 links "verified trajectories" per row, so the public viewer for Terminal-Bench trajectories is Harbor's own viewer, hosted.

## 3. Hooks and export paths for external observability tools

Harbor has no OpenTelemetry, Langfuse, Weave, Braintrust, Phoenix or LangSmith integration of its own. Grepping `$H` for those names finds only `environments/langsmith.py` and `environments/wandb.py`, which are *sandbox providers* (places to run the container), not trace exporters. The `telemetry.py` module is Harbor's own product analytics to PostHog, off with `HARBOR_TELEMETRY=0`.

What Harbor does offer, all in the installed source:

- Trial lifecycle hooks in Python: `Job.on_trial_started/on_agent_started/on_agent_ended/on_verification_started/on_trial_ended` (`$H/job.py:182-206`) receive a `TrialHookEvent` with the config, the partial `TrialResult` and the trial directory (`$H/trial/hooks.py`). A `LogCallback` receives streamed log chunks per phase. These are only reachable when you drive Harbor from Python rather than the CLI.
- Job plugins from the CLI: `harbor run --plugin module:ClassName` loads a `JobPlugin` subclass with `on_job_start(job)` and `on_job_end(job_result)` (`$H/cli/job_plugins.py`); `on_job_start` gets the `Job` object, so a plugin can register the trial hooks above. `harbor plugins list` shows installed ones; the only bundled plugin is the Hub uploader (`$H/cli/plugins/harbor_hub.py`).
- Env var pass-through to the agent: `harbor run --ae KEY=VALUE` (repeatable). The values become the agent's `extra_env`, and the trial applies them as a scoped exec environment around the agent phase (`$H/trial/trial.py:504-533`), so every command the agent installer runs, including `claude -p ...`, sees them. `--env-file .env` loads keys into Harbor's own process and the agent reads its API key from there. `--ve` does the same for the verifier.

That last point is the route for Claude Code's native OpenTelemetry export. Claude Code emits OTLP metrics and events when `CLAUDE_CODE_ENABLE_TELEMETRY=1` and the `OTEL_*_EXPORTER` and `OTEL_EXPORTER_OTLP_ENDPOINT` variables are set, with spans behind `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` and `OTEL_TRACES_EXPORTER=otlp`; content flags `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_TOOL_CONTENT` control whether prompts, tool names and tool input/output are included (https://code.claude.com/docs/en/monitoring-usage). Passing them with `--ae` should work in principle, with three caveats I could not fully verify:

1. Harbor sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` on every claude-code run (`claude_code.py:1830`). The Claude Code data-usage docs describe that flag as bundling the Anthropic-bound telemetry switches (`DISABLE_TELEMETRY`, error reporting, auto-update), and nothing in the monitoring docs says it touches the user's OTLP exporter, but I found no explicit statement either way (https://code.claude.com/docs/en/data-usage). A five-minute test with `OTEL_METRICS_EXPORTER=console` inside a container would settle it.
2. Network. This repo's tasks run the agent under `network_mode = "allowlist"` with only the model API hosts allowed (`tasks/*/task.toml`, `docs/decisions.md` 2026-09-09). A collector on the Mac would need to be added with `--allow-agent-host <ip or host>` at run time, and there is no `host.docker.internal` in Harbor's compose files (`$H/environments/docker/*.yaml`), so reaching the host relies on the Docker runtime providing that name. Under OrbStack it normally does, but it is untested here.
3. Claude Code's OTel events are metrics and log events, not the full conversation. Token counts, cost, tool names and (opt-in) tool arguments arrive live; the assistant's text only with `OTEL_LOG_ASSISTANT_RESPONSES=1`. For "what did the agent do" the ATIF file after the run is more complete than the live stream.

Codex has no equivalent documented OTel export that I checked, so a live-export approach would cover only one of the two harnesses this repo baselines.

Two third parties have built the after-the-run path instead:

- Arize Phoenix: `upload_atif_trajectories_as_spans(client, [trajectory], project_name=...)` in `arize-phoenix-client` 2.3.0+ converts an ATIF file into an OpenTelemetry span tree (AGENT root, LLM spans for decisions, TOOL spans as siblings, sub-agents linked into the same trace, ids derived from `session_id` so re-upload is idempotent). The current source says it supports ATIF v1.0 through v1.7, which matches our files; v1.8 audio fields are not supported (https://arize.com/docs/phoenix/release-notes/04-2026/04-03-2026-atif-trajectory-upload, source at https://github.com/Arize-ai/phoenix/tree/main/packages/phoenix-client/src/phoenix/client/helpers/atif). Phoenix runs locally with `pip install arize-phoenix && phoenix serve`.
- Comet Opik: `opik harbor run <harbor options>` wraps Harbor. Its tracker does not use the hook API; it monkey-patches `Trial.run`, `Verifier.verify` and the ATIF `Step` class so that every step becomes an Opik span as it is constructed, and the verifier rewards become feedback scores on the trace (https://github.com/comet-ml/opik/blob/main/sdks/python/src/opik/integrations/harbor/opik_tracker.py, docs https://www.comet.com/docs/opik/integrations/harbor). Patching internals means it can break on a Harbor version bump.

There is an open proposal to give ATIF a standard OpenTelemetry mapping, opened June 2026 by a Red Hat engineer, which says plainly that today "the conversion is bespoke and incomplete until the conventions exist" (https://github.com/open-telemetry/semantic-conventions-genai/issues/338).

## 4. Third-party viewers for ATIF and Terminal-Bench output

- Harbor's own viewer (section 2) is the reference. The Terminal-Bench leaderboard's per-row trajectory links open it.
- `Slimshilin/ATIF-trajectory-viewer` (https://github.com/Slimshilin/ATIF-trajectory-viewer, demo at https://atif-trajectory-viewer.vercel.app/): a static browser-only React app by a Harbor core contributor, Apache-2.0. It shows a step timeline with message, reasoning, tool calls and observations, plus a reconstructed view of the container filesystem inferred from the tool calls, which the README warns "is not always faithful". Loads ATIF JSON from a `public/runs/` folder or a dropped Harbor task zip. Useful as a reference implementation if we build our own.
- trajectories.sh (https://www.trajectories.sh/): a hosted service. `npm i -g trajectories-sh`, then `trajectories-sh upload trajectory ./my-run/` pushes a Harbor job directory and each upload gets an embedded Harbor viewer with private, unlisted or public sharing. Operator and pricing are not stated on the page.
- A Harbor issue asks for viewer support of non-linear history split across files (https://github.com/laude-institute/harbor/issues/239), which shows the viewer is the maintained surface and ATIF continuation is still rough.

## 5. What the broader ecosystem does

SWE-agent writes one `.traj` JSON per instance with, per step, `response`, `thought`, `action`, `observation`, `state` (open file, cwd) and `query` (the full message history sent to the model). It ships two viewers: `sweagent inspect` (terminal pager, vim keys) and `sweagent inspector` (local web server, default port 8000) that reads a `trajectories/` folder and overlays `results.json` pass marks (https://github.com/SWE-agent/SWE-agent/blob/main/docs/usage/trajectories.md, https://github.com/SWE-agent/SWE-agent/blob/main/docs/usage/inspector.md). Its step shape maps almost one-to-one onto an ATIF step (thought = `reasoning_content`, action = a tool call, observation = observation), but there is no importer either way.

Inspect AI (UK AISI) stores an `EvalLog` per task run in a binary `.eval` or `.json` file: header (`eval`, `plan`, `results`, `stats`) plus `samples`, each with `messages`, a full `events` transcript (model calls, tool calls, sandbox exec, scoring), `scores` and metadata. `inspect view` serves a rich browser UI over a log directory. The public API `write_eval_log(EvalLog)` lets you construct a log from external data, so an ATIF to Inspect converter is possible: one Harbor trial becomes one sample, steps become `messages` and `events`, `reward.json` becomes the score (https://inspect.aisi.org.uk/eval-logs.html). Nobody has published such a converter that I found.

OpenAI's `evals` repo writes per-sample JSONL records and has no bundled trajectory UI; it is not a fit for multi-step agent runs and I did not pursue it further.

Prime Intellect's `verifiers` writes each eval run to `outputs/evals/<env>--<model>/<id>/results.jsonl` plus `metadata.json` and ships `vf-tui` (also `prime eval tui`), a terminal UI with a rollout viewer, search and per-turn timing, plus `prime eval push` to their hub (https://www.mintlify.com/primeintellect-ai/verifiers/cli/eval-tui, https://github.com/PrimeIntellect-ai/verifiers/releases). Its records are prompt/completion/reward rows in chat-message form, so an ATIF trajectory could be flattened into one, but it is a terminal viewer for their own format, not a general trajectory tool.

Langfuse and W&B Weave are trace databases with UIs that ingest OpenTelemetry directly: Langfuse at `<host>/api/public/otel` (OTLP over HTTP only, basic auth from the project keys; self-host with Docker Compose) (https://langfuse.com/integrations/native/opentelemetry), Weave at `https://trace.wandb.ai/otel/v1/traces` with the API key in a header and `wandb.project` as a resource attribute (https://docs.wandb.ai/weave/guides/tracking/otel). Both store per span: name, parent, start/end, inputs, outputs, model, token usage and cost, following the OTel GenAI semantic conventions. Neither ingests ATIF; getting ATIF into them means either Claude Code's live OTLP export (section 3) or a small script that walks the ATIF steps and emits spans with the OTel SDK, which is exactly what Phoenix's helper already does for Phoenix.

## 6. Assessment and recommendations

Is there a standard? For the file on disk, yes: ATIF is now the interchange format, thirty-one Harbor agents emit it, Phoenix and Opik consume it, an OTel convention is being drafted around it, and a third-party viewer plus a hosting service exist. For the viewer, no: every framework (Harbor, SWE-agent, Inspect, verifiers) ships its own UI over its own log shape, and the cross-tool path is "convert to OTel spans and use a trace database", which is still described by its own proponents as bespoke. The practical consequence for this repo is that we should not write a viewer, because Harbor's is already installed and works on our `jobs/` directory as-is.

Recommended, in order of effort:

1. Use `harbor view jobs` today. Zero code. It gives per-trial step replay, verifier output, the file browser for `claude-code.txt` and the native session, and the cross-agent comparison grid that reads our extra metrics from `reward.json`. Pair it with `harbor analyze <job> --failing` with a small rubric written for our benchmark ("did the agent run the pipeline through ZenML or bypass it?", "did it read the offline docs?") to get LLM-judged summaries of failures, and `harbor trial handoff <trial>` when a single failure needs interactive digging. Document all three in `CLAUDE.md`. Trade-off: local only and per-machine; nothing is shared or persisted beyond `jobs/`.
2. Push ATIF into Phoenix for cross-run analysis. `phoenix serve` locally, then a ~30-line script (or a `--plugin` JobPlugin with an `on_trial_ended` hook) that calls `upload_atif_trajectories_as_spans` for each trial and attaches `reward.json` as span attributes. This gives a queryable trace store: filter all trials by tool name, plot tokens against reward, compare bare vs mcp conditions as projects. Trade-off: a second UI to run, and the mapping loses Harbor-specific context (verifier logs, artifacts) unless we attach it ourselves; version drift between ATIF and the helper is a real risk (it lagged v1.7 for a while).
3. Only if live monitoring of long research tasks matters: enable Claude Code's OTel export with `--ae CLAUDE_CODE_ENABLE_TELEMETRY=1 --ae OTEL_METRICS_EXPORTER=otlp --ae OTEL_EXPORTER_OTLP_ENDPOINT=http://<host>:4318 ...` plus `--allow-agent-host <host>`, pointed at a local collector or Langfuse. Trade-off: claude-code only, needs the network and non-essential-traffic questions in section 3 answered first, and it duplicates what ATIF already records after the fact. I would not start here.

Not recommended: a custom static HTML viewer (duplicates `harbor view` and the Slimshilin project), trajectories.sh for now (unclear operator, and `harbor upload` to Harbor Hub already gives private hosted sharing if we ever need it), and an ATIF to Inspect converter (a fair amount of work to gain a UI we would use less than Harbor's own).

Follow-ups this research surfaced: `scripts/analyse_trajectories.py` could read `agent/claude-code.txt`'s init event to record the MCP server list and permission mode per trial, and the `--artifact` flag could pull the ZenML store's SQLite file out of each trial so graders' evidence is browsable in the viewer's Artifacts tab.
