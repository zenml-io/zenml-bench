# Kitaru tasks

Harbor tasks in which a coding agent has to use real Kitaru at a pinned version. In progress: four tasks so far, all on the `storefront` world: `c1-rule-from-builtins`, `c2-finding-to-check`, `c3-evaluator-is-wrong`, `c4-backfill-one-release`. Decisions and what each spike showed are in `docs/decisions.md` (entries dated 2026-11-20).

## Layout

- `base/Dockerfile`, `base/files/` — the base image every task starts from: PostgreSQL, Kitaru (server, worker, CLI, MCP), the PydanticAI adapter, the agent CLIs, the wheels for Kitaru's built-in plugins, the docs. `files/start.sh` starts Postgres, the server and a worker and is safe to run repeatedly; `files/stop.sh` stops them.
- `worlds/<name>/` — one fictional company, reused by many tasks. `story.py` plans every session from a seed (no model, no agent run) and also writes the hidden sessions a grader imports. `load.py` imports the history while the image is built. `workspace/` is what the agent finds in `/app`. `Dockerfile.world` is the image section that does the loading.
- `tasks/<id>/` — a Harbor task. `world` names its world. `environment/` is generated by `scripts/sync_env.sh` and must not be edited by hand. The same script writes the world's answer key to `tests/fixtures/ground_truth.json`. Hidden sessions for graders that run agent code come from `story.py hidden --task <c2|c3> --seed N --out tasks/<id>/tests/fixtures`. After changing a world, re-sync and re-check every task on it.
- `checks/kitaru_checks.py` — helpers every grader shares; each task carries a copy in `tests/`.
- `scripts/sync_env.sh <task>` — rebuilds a task's `environment/` from `base/` and its world. Run after editing either.
- `scripts/grade_local.sh <task> [script.sh ...]` — runs the grader in local Docker against a fresh container per script (about 45 s each). Use it for the four checks before spending Modal time.
- `spikes/` — throwaway tasks that each proved one mechanism. Not benchmark tasks; never published.

## Running

```
kitaru/scripts/sync_env.sh kitaru/tasks/c2-finding-to-check
T=kitaru/tasks/c2-finding-to-check
BUILD=1 kitaru/scripts/grade_local.sh $T $T/solution/solve.sh "" $T/solution/alternatives/*.sh $T/tests/shortcuts/*.sh
MODAL_ENVIRONMENT=dev uv run scripts/verify_task.py $T --env modal -n 4 --job-prefix kverify
```

## Rules a Kitaru task follows

- The agent runs as user `agent`, never root (`[agent] user = "agent"`). It reaches Kitaru over HTTP only.
- `[environment.healthcheck] command = "/opt/kitaru-bench/start.sh"` starts everything; the image starts nothing by itself.
- `[environment] network_mode = "allowlist"`, not `"no-network"` (Modal cannot add a host list to a sandbox created without one).
- The grader stops the agent's processes, starts its own worker as user `grader`, and runs the agent's registered work on inputs the agent never saw.
- Code the agent registered (an evaluator, an importer) runs *during grading*, on the same disk as the answer key. `start_grader_worker()` first makes `/tests`, `/solution` and `/logs` readable by root only. Every task that runs agent code while grading ships a `read_grader_labels.sh` shortcut that tries to open the answer key and must score 0.
- A Dockerfile `RUN` line must not contain the text `uvicorn kitaru.server` or `kitaru worker start`: `start.sh` looks for those with `pgrep -f` and would find the build shell itself.
- The answer key never enters the image: `story.py` stays out, and only counts (`plan.json`) go in.

## Publishing the base image

The base image goes to `ghcr.io/zenml-io/kitaru-bench-base:<kitaru pin>-<revision>`, for `linux/amd64` (Modal) and `linux/arm64` (Macs). Every step, in order; do not skip the scans.

```
git status --short                     # must be clean: the image is built from the commit, not from the working folder
X=$(mktemp -d); git archive HEAD kitaru/base | tar -x -C $X
for A in amd64 arm64; do docker buildx build --platform linux/$A --load -t ghcr.io/zenml-io/kitaru-bench-base:<tag>-$A -f $X/kitaru/base/Dockerfile $X/kitaru; done
for A in amd64 arm64; do uv run kitaru/scripts/scan_image.py ghcr.io/zenml-io/kitaru-bench-base:<tag>-$A --secrets-from .env; done    # both must print CLEAN
gh auth token | docker login ghcr.io -u <login> --password-stdin        # needs the write:packages scope
for A in amd64 arm64; do docker push ghcr.io/zenml-io/kitaru-bench-base:<tag>-$A; done
docker buildx imagetools create -t ghcr.io/zenml-io/kitaru-bench-base:<tag> ghcr.io/zenml-io/kitaru-bench-base:<tag>-{amd64,arm64}
# pull it back and scan what the registry serves
for P in linux/amd64 linux/arm64; do docker pull --platform $P ghcr.io/zenml-io/kitaru-bench-base:<tag>; uv run kitaru/scripts/scan_image.py ghcr.io/zenml-io/kitaru-bench-base:<tag> --platform $P --secrets-from .env; done
```

A new package on GHCR is private. Making it public is Alex's step, in the package's settings page on GitHub, after the scans above are clean. A published tag is never overwritten: a change to `base/` gets a new revision number.

`scan_image.py` searches every layer (a file deleted by a later build step is still in the earlier layer), the build history and the image configuration. It blocks on: any secret value held on this machine (the `.env` files given, secret-looking shell variables, the credential files of `gh`, Modal, Hugging Face, Prime, Codex, Docker and others), plain or base64; the home path, login name, git email or host name; credential-style files; and pattern-scanner hits outside third-party package folders. It needs `rg` and uses `trufflehog` when installed, with verification off so no candidate string is sent anywhere.
