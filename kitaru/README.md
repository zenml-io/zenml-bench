# Kitaru tasks

Harbor tasks in which a coding agent has to use real Kitaru at a pinned version. In progress: thirty-seven tasks so far, on five worlds. On `helpdesk-live` (a helpdesk agent that really runs, recorded through the real adapter, with a finance service that records every refund): the first four replay tasks, `f1-replay-without-refunding`, `f2-fix-euro-with-evidence`, `f3-refunds-far-too-large`, `f4-experiment-keeps-failing`. On `helpdesk-services` (the same assistant one release on, with an order service that is slow, serves four requests at a time and counts every lookup): four more replay tasks, `f5-stop-asking-twice`, `f6-run-them-together`, `f7-where-low-effort-is-safe`, `f8-pick-between-two-fixes`, and four setup tasks, `o1-nothing-is-running`, `o2-record-this-agent`, `o3-make-it-replayable`, `o4-record-a-langgraph-agent`. On `clinic` (a veterinary chain's appointment assistant, 3,211 conversations, a repository with dated commits): five diagnosis tasks, `d1-wrong-clinic`, `d2-was-it-the-release`, `d3-answers-cut-off`, `d4-what-broke`, `d5-did-the-hotfix-work`. On `storefront`: The checks family: `c1-rule-from-builtins`, `c2-finding-to-check`, `c3-evaluator-is-wrong`, `c4-backfill-one-release`, `c5-agree-with-reviewers`, `c6-check-before-merge`. Four diagnosis tasks, where the answer is a Kitaru cohort (`d6-refunded-too-much`, `d7-slower-no-release`, `d9-retries-or-traffic`) or an investigation with verdicts (`d8-six-to-read`). On `exports` (a courier company with two assistants: one writes a home-made trace log, the other was traced with Langfuse): the import family, `i1-import-an-export`, `i2-one-ticket-one-session`, `i3-write-an-importer`, `i4-nightly-import-twice`, `i5-invoice-does-not-match`. Five harder variants of tasks that both large models passed every time: `c1h-two-rules-from-builtins`, `c7-fix-check-then-backfill` (C3 and C4 in one), `d8h-triage-check-failures`, `i3h-messy-log`, `i4h-strays-at-scale`. Decisions and what each spike showed are in `docs/decisions.md` (entries dated 2026-11-20 and 2026-11-21).

## Layout

- `base/Dockerfile`, `base/files/` — the base image every task starts from: PostgreSQL, Kitaru (server, worker, CLI, MCP), the PydanticAI adapter, the agent CLIs, the wheels for Kitaru's built-in plugins, the docs. `files/start.sh` starts Postgres, the server and a worker and is safe to run repeatedly; `files/stop.sh` stops them.
- `worlds/<name>/` — one fictional company, reused by many tasks. `story.py` plans every session from a seed (no model, no agent run) and also writes the hidden sessions a grader imports. `load.py` imports the history while the image is built. `workspace/` is what the agent finds in `/app`. `Dockerfile.world` is the image section that does the loading.
- `tasks/<id>/` — a Harbor task. `world` names its world. An optional `plants` file names an extra set of planted problems (`diagnosis` for the D tasks): `sync_env.sh` passes it to `story.py history --plants`, so the D tasks' history is the C tasks' history plus those problems, and the C tasks' images do not change. `environment/` is generated by `scripts/sync_env.sh` and must not be edited by hand. The same script writes the world's answer key to `tests/fixtures/ground_truth.json`. Hidden sessions for graders that run agent code come from `story.py hidden --task <c2|c3> --seed N --out tasks/<id>/tests/fixtures`. After changing a world, re-sync and re-check every task on it. An optional `workspace/` folder is laid over the world's workspace for that task, and an optional `setup/` folder plus `Dockerfile.task` prepare Kitaru's state while the image is built (an agent, earlier imports, a cohort); what such a setup records for the grader goes to `/etc/kitaru-bench/<task>.json`, readable by root only.
- `checks/kitaru_checks.py` — helpers every grader shares; each task carries a copy in `tests/`.
- `scripts/sync_env.sh <task>` — rebuilds a task's `environment/` from `base/` and its world. Run after editing either.
- `scripts/grade_local.sh <task> [script.sh ...]` — runs the grader in local Docker against a fresh container per script (about 45 s each). Use it for the four checks before spending Modal time.
- `spikes/` — throwaway tasks that each proved one mechanism. Not benchmark tasks; never published.

## Running

```
kitaru/scripts/sync_env.sh kitaru/tasks/c2-finding-to-check
T=kitaru/tasks/c2-finding-to-check
BUILD=1 kitaru/scripts/grade_local.sh $T $T/solution/solve.sh "" $T/solution/alternatives/*.sh $T/tests/shortcuts/*.sh
MODAL_ENVIRONMENT=dev uv run scripts/verify_task.py $T --env modal -n 4 --job-prefix kverify
```

## Rules a Kitaru task follows

- The agent runs as user `agent`, never root (`[agent] user = "agent"`). It reaches Kitaru over HTTP only.
- `[environment.healthcheck] command = "/opt/kitaru-bench/start.sh"` starts everything; the image starts nothing by itself.
- `[environment] network_mode = "allowlist"`, not `"no-network"` (Modal cannot add a host list to a sandbox created without one).
- The grader stops the agent's processes, starts its own worker as user `grader`, and runs the agent's registered work on inputs the agent never saw.
- Code the agent registered (an evaluator, an importer) runs *during grading*, on the same disk as the answer key. `start_grader_worker()` first makes `/tests`, `/solution` and `/logs` readable by root only. Every task that runs agent code while grading ships a `read_grader_labels.sh` shortcut that tries to open the answer key and must score 0.
- A Dockerfile `RUN` line must not contain the text `uvicorn kitaru.server` or `kitaru worker start`: `start.sh` looks for those with `pgrep -f` and would find the build shell itself.
- The answer key never enters the image: `story.py` stays out, and only counts (`plan.json`) go in.
- A world grows without reshuffling: new attributes are drawn from a second random stream seeded by the session's id, and existing draws stay where they were. After a world change, compare old and new histories session by session (decisions.md, C5 and C6 entry).
- Generate task scripts with Python or `printf '%s\n'`, never zsh `echo "$VAR"`: it turns `\n` inside the variable into a line break.

## Publishing the base image

The base image is on Docker Hub, `zenmldocker/kitaru-bench-base:<kitaru pin>-<revision>`; `base/IMAGE` holds the full name with its digest. It is built for `linux/amd64` (Modal) and `linux/arm64` (Macs). Every step, in order; do not skip the scans.

```
git status --short                     # must be clean: the image is built from the commit, not from the working folder
X=$(mktemp -d); git archive HEAD kitaru/base | tar -x -C $X
for A in amd64 arm64; do docker buildx build --platform linux/$A --load -t zenmldocker/kitaru-bench-base:<tag>-$A -f $X/kitaru/base/Dockerfile $X/kitaru; done
for A in amd64 arm64; do uv run kitaru/scripts/scan_image.py zenmldocker/kitaru-bench-base:<tag>-$A --secrets-from .env; done    # both must print CLEAN
docker login                           # as an account that may push to the zenmldocker namespace
for A in amd64 arm64; do docker push zenmldocker/kitaru-bench-base:<tag>-$A; done
docker buildx imagetools create -t zenmldocker/kitaru-bench-base:<tag> zenmldocker/kitaru-bench-base:<tag>-{amd64,arm64}
# pull it back and scan what the registry serves
for P in linux/amd64 linux/arm64; do docker pull --platform $P zenmldocker/kitaru-bench-base:<tag>; uv run kitaru/scripts/scan_image.py zenmldocker/kitaru-bench-base:<tag> --platform $P --secrets-from .env; done
```

A new repository on Docker Hub is public as soon as it is pushed, so the scans come before the push. Pulls of a public Docker Hub image cost the publisher nothing. A published tag is never overwritten: a change to `base/` gets a new revision number.

`scan_image.py` searches every layer (a file deleted by a later build step is still in the earlier layer), the build history and the image configuration. It blocks on: any secret value held on this machine (the `.env` files given, secret-looking shell variables, the credential files of `gh`, Modal, Hugging Face, Prime, Codex, Docker and others), plain or base64; the home path, login name, git email or host name; credential-style files; and pattern-scanner hits outside third-party package folders. It needs `rg` and uses `trufflehog` when installed, with verification off so no candidate string is sent anywhere.
